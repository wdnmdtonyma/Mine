页面 · 按钮 · 表单 · 流程 → “帮我完成这件事”

今天我想借过去三年做 Agent 产品的几段经历，跟大家分享一些实际的工作经验，以及我对 AI 产品逐渐形成的一点认知。

这几年有一个很明显的变化：越来越多原本分散在页面、按钮和流程里的功能，正在被放进一个对话框。

过去，用户要找到正确的入口，理解页面和流程，再一步步完成操作。现在，用户可能不再关心功能在哪里，只需要说一句：“我想完成这件事。”

这会带来今天最想讨论的问题：当用户只需要表达目的，产品经理还需要设计什么？

对话框只是入口，任务执行环境才是主体。

从一句话，直到任务真正完成

但从“说一句话”到“事情真的完成”，中间还有大量工作：理解目标、补齐信息、选择路径、调用工具、处理权限、面对失败，以及判断结果能不能交付。

这些工作没有随着页面消失。它们只是从用户看得见的页面和操作流程，转移到了用户看不见的系统内部。

所以我这几年越来越明确的判断是：对话框只是 Agent 产品的入口，任务执行环境才是 Agent 产品真正的主体，也会成为产品经理越来越核心的设计对象。

为了把这个判断说清楚，在正式讲项目之前，我们先把这句用户输入往下展开：从一句话到最终结果，中间到底发生了什么？

05 · ACT执行行动工具在真实环境中做事
06 · OBSERVE接收反馈成功与失败都重新写回 Context

The simplest useful mental model

用户只说一句话，
Agent 到底经历了什么？

Agent ≠ 一次调用模型
Agent = 观察 → 判断 → 行动 → 再观察
  • 模型并不“记得”刚才发生了什么；每一轮都要重新组织它能看到的内容。
  • 工具失败不是旁路，而是帮助 Agent 修正下一步的主反馈通道。
  • 模型说“做完了”不等于任务完成；测试、规则和人工确认仍可把它打回。

在进入项目之前，先用几分钟对齐一张地图。用户发出一句话以后，系统先定义任务，再组装模型能看到的全部内容。

模型每次只判断下一步：答、问，还是调用工具。工具把真实环境的结果写回来，系统再重新问模型。这个循环一直持续到满足结束条件。

强调三个点：Agent 不是一次模型调用；失败结果是纠正回路的一部分；模型说完成不代表真的完成。

产品可以直接设计五件事：目标、Context、行动空间、循环规则和反馈。模型具体会怎么理解、怎么规划，我们只能间接影响；用户含糊、数据缺失、第三方失败则只能管理，无法消除。

Case 01 · Aime04 / Individual Task
01
字节内部通用 Agent 产品

模型已经会写代码了，
为什么仍然交付不了
一个需求？

因为代码生成只是 Loop 中的一次 Action。任务真正结束之前，还有环境、测试、验证、调试、失败恢复和 Handoff。

7.5 万周活跃用户
90%研发群体覆盖

Aime 是面向字节研发群体的通用 Agent，最后做到周活 7.5 万、覆盖 90% 的研发群体。

但今天不重点讲规模，而讲一个更本质的问题：模型已经能写出不错的代码，为什么用户仍然不能把一个需求完整交给它？

后来我们发现，生成代码只是一次 Action。产品要解决的是“事情能不能真正做完”。

Aime · 一条脱敏任务链06 / Trace

A failure is not the end; it is new context

一次“真正交付”，中间发生了什么？

YOU

“根据需求改造一个接口，并保证相关测试通过。”

脱敏后的典型链路
01

定义完成标准

先把“改完”翻译成 Spec、范围和必须通过的检查。

TASK
02

组装 Context

拉取工作项、仓库、相关文档、团队规范和历史状态。

CONTEXT
03

拆解并派工

探代码、方案、实现和验证，可以串行，也可以并行。

LOOP
04

进入环境执行

Worker 改文件、跑命令，并调用研发工具链。

ACTION
05

第一次测试失败

失败原因不是丢掉，而是作为工具结果重新写回 Context。

FEEDBACK
06

定位、修改、重跑

规划者根据新证据换路；必要时追问或请求人接管。

RECOVER
07

验证通过并交付

代码、测试结果、产物和剩余风险一起 Handoff。

DELIVER
关键不是“一次成功”

而是系统能不能看见失败、理解失败，并在可控边界里恢复——这才是长任务真正的产品体验。

用一条脱敏的典型任务把架构跑起来。用户说“改造接口并保证测试通过”。系统首先要把“做完”变成可判断的标准。

随后组织 Context、拆解任务、派 Worker 到云环境里执行。重点停在第五步：第一次测试失败。失败不是事故旁路，而是重新规划最重要的新证据。

Agent 根据失败定位、修改、重跑，最后把代码、测试结果和风险一起交给用户。真正值得讲的是它如何失败和恢复，而不是 Demo 里的一次成功。

Aime · 关键取舍07 / Product Decisions

Three choices that shaped the product

真正决定产品形态的，
不是做了哪些功能，
而是在哪里承接不确定性。

交付

继续优化生成，还是补齐任务闭环？

更好的回答 / 代码↓ 我们选择测试、验证、调试 Harness

继续提高“写得像不像”只是在优化一个节点。生产可用的关键，是写完以后能不能被验证并交付。

代价：建设更重、更慢；收益：成功标准从主观好感变成客观结果。
扩展

每个场景硬编码，还是建设能力生态？

核心团队把能力全部做死↓ 我们选择Skills 教方法 · MCP 接工具

业务知识和做事方法可以持续沉淀，真实工具也能不断接入；Agent 根据任务动态组装 Worker。

边界：Skill 解决“怎么做”，MCP 解决“手够不够得着”，两者不能互相替代。
可控

完全自治，还是设计阶段性 Handoff？

让 Agent 一直跑到自称完成↓ 我们选择SDD + 确认点 + 本地/云端接力

长任务不是简单地让 Agent 跑得更久，而是明确什么时候对齐方案、何时并发、何时确认、何时交还给人。

取舍：自由度越高越灵活；责任越重，越需要收紧动作空间和验证门。

Aime 最值得复盘的是三个选择。

第一，从继续卷生成质量转向补齐测试、验证、调试的闭环。第二，不为每个场景重做 Agent，而用 Skills 和 MCP 建设可扩展生态。第三，不迷信完全自治，通过 SDD、确认点和 Handoff 管理风险。

规模指标证明用户愿意来，但真正的产品指标还要看任务成功、返工、重试和中途接管。这一点也会引出 Flux。

新的反直觉问题

人人都在用 Agent，
为什么组织交付

Aime 解决了个人怎么把任务交给 Agent。覆盖绝大部分研发之后，我们原本以为组织交付也会自然提升。

但出现了一个反直觉现象：大家写代码越来越快，需求从提出到上线却没有同比例变快。于是问题从个人 Loop 扩大到组织 Loop。

Flux · 立项洞察09 / Bottleneck Transfer

Local optimization is not system optimization

个人提效 ≠ 组织提效，
瓶颈只是在价值链上移动。

01

产品

问题定义、需求澄清、业务 Context

02

设计

交互、状态、素材与设计产物

03

研发

Agent 写代码已经成为高频工作方式

04

测试

接口、GUI、造数、回归仍有大量断点

05

上线

调试、发布、责任节点与最终验证

上产品与设计的产出，不能直接成为下游 Agent 的 Context。
下测试与验证 Harness 没补齐，代码写得快也排队。
数Token 和使用量证明“在用”，不能直接证明“交付更快”。

把需求价值链摊开看，研发环节被 Agent 显著加速，但上游产品和设计的产物并没有自然变成可消费的 Context，下游测试、造数、GUI 验证、调试和上线仍然断裂。

这就是木桶效应：局部环节越快，等待越集中到其他环节。Token 消耗、周活都只是领先指标，最终还要看需求流转和交付周期。

Aime：设计一个人的任务环境　→　Flux：设计人、Agent 与组织共同工作的环境 周活破万是领先指标，不是终点

Flux 的方案分三层。第一层是共享 Context，让产品、设计、研发和测试的产物成为同一个工作现场，而不是散落的附件。

第二层不是再造一个 Agent，而是统一调度 Codex、Claude Code 等成熟 Agent。第三层补齐 Spec、测试、造数、调试和部署 Harness。

原来优化的是模型与工具之间的 Loop；现在优化的是人、Agent 和组织之间的 Loop。

Flux · 关键取舍11 / Product Decisions

Trust before magic; leverage before reinvention

组织协作产品里，
“更聪明”未必是更好的第一步。

决策 01 · 预期管理

先做“聪明的协作助理”吗？

主动催办、识别阻塞、帮团队协调一切
vs
简单可靠的共享 Context 与协作空间

协作助理属于“没有无所谓，做不好就会伤害信任”的能力。先把简单但确定的事情做好，让产品建立专业预期。

低误伤可解释可验证先建立信任
决策 02 · 生态位

要重新自研一个完整 Agent 吗？

自研模型伴生 Agent，重建用户习惯
vs
统一编排 SOTA Agent，把精力放在协作层

自研起步慢，用户迁移成本真实存在，也很难长期碾压能力前沿。Flux 选择投资在共享 Context、协作和后链路 Harness。

启动速度用户习惯SOTA 能力差异化资产
领先指标周活破万 · 用户持续回来→需求流转与交付周期终局指标

Flux 有两个我认为很有产品味道的决定。

第一，团队有人想先做主动协作助理。听起来更性感，但它是做不好就伤信任的能力，所以先做简单可靠的共享区。

第二，不自研完整 Agent，而是编排用户已经熟悉的 SOTA Agent。我们把差异化放在共享 Context、组织协作和研发后链路。

周活破万说明用户持续感到价值，但不能把它当终点。最终北极星仍然是需求从提出到上线的交付效率。

产品经理的变化13 / Takeaways

Three shifts for product managers

Agent 改变的不是一个入口，
而是产品工作的基本单位。

Shift 01 · 设计单位

从功能，
到任务。

这个功能有哪些页面？用户究竟想完成什么？什么才算完成？

任务的目标、边界、成功标准和红线，开始早于页面，也决定后面的系统设计。

Shift 02 · 责任边界

从交互，
到执行环境。

用户如何点击和流转？Agent 看见什么、能做什么、何时停下？

Context、工具、权限、Loop、异常恢复和验证，不再只是工程细节，而是产品体验本身。

Shift 03 · 衡量方式

从使用，
到完成。

有多少人打开和使用？任务成功了吗？交付真的变快了吗？

周活和留存仍然重要，但只是必要条件；返工、接管、成功率和业务交付才是终局。

把结论落到产品经理身上，有三个变化。

第一，设计单位从功能和页面变成任务与成功标准。第二，责任边界从交互扩展到 Context、工具、权限、循环和验证。第三，衡量方式从有没有使用走向有没有完成、业务是否真的变快。

页面依然重要，但它只是整个产品责任的一部分。

最后一句14 / Closing

Agent 时代，
产品经理不是在给模型设计一个入口；
而是在给任务设计一个能够完成它的世界。

页面越简单，越意味着我们把更多复杂性从用户手里接了过来，放到了系统内部。
