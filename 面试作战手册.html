// 五句救命绳 —— 进场前最后看一眼

  1. 动机锚在发行场景本身的价值——多语言多市场、内容产能、效果全可量化。基模两个字全场禁言。
  2. 被质疑没有发行经验，用「同构问题」重构：我在另一个场景完整验证过同一类问题的解法。
  3. Case 题永远先拆业务链路、后讲 AI 能力——research / 分析 / 生成是手段，链路提效才是目的。
  4. 被捅指标时让步只让边界、不让价值：先立区别顶回去，再认边界，最后给时间表。
  5. 复合问题先记关键词，答一个勾一个——今晚三次漏答子问题，这是你压力下的系统性漏洞。

R1 · 自我介绍 + 为什么来做发行 AI 5.5 / 10

【题】两三分钟总结你三年 Agent 经验的主线；为什么放弃字节的好绩效来做游戏发行 AI？你对「发行 AI 化」的理解是什么？

【保留】做对的部分
  • 「24 单点排障 → 25 通用 Agent → 26 团队协作」的时间线，且每次形态切换都锚定在模型能力变化上——这是你自我介绍最大的资产，原样保留。
【雷】踩过的坑
  • 动机答成「想离基模近」——面试官听到的是：真正想去的不是这儿，进来就是跳板。追问「三年碰不到基模还来吗」两轮回避，比答错更减分。
  • 泄露前司战略判断（「内场会被豆包吞并」）——今天能这么聊字节，明天就能这么聊米哈游。离职原因说到「内部能力收敛整合、个人空间收窄」为止。
  • 漏答半个问题（发行 AI 化的理解），且把发行错误类比成研发流水线，还以「我不太确定对不对」收尾——把展示题答成了求助题。
  • 「想多了解不同行业」「试一试」——行业体验卡心态，这三个字不许再出现。
【示范】动机 · 30 秒
「我看这个 JD 时的判断是：发行可能是游戏行业里 AI 落地价值密度最高的场景——多语言多市场、内容产能需求巨大、流程重复度高，而且效果全部可量化。这和我三年做的事本质相同：把复杂业务拆成 Agent 可接管的环节，建好 Harness 保证生产环境真实可用。我在研发场景完整验证过一遍这套方法论，想在一个业务价值更外显的场景再做一遍。行业经验我坦承是缺口，但我已经开始补——（HoYoLAB 的具体观察放这里）。」
【示范】发行 AI 化的理解 · 90 秒 · 总—分—总
开场定框架 · 10s 「发行 AI 化不是做一个 AI 工具，而是沿着本地化、买量、社区、客服这几条业务链路，在版本循环里逐条做智能化改造。」 具象化：一个版本周期 · 40s 「拿星铁一个新版本的六周讲：版本文本和 PV 要在死线前翻成十几种语言、过各地区文化合规；买量团队要给各市场备几十上百条素材，投几天就衰退；上线当天 HoYoLAB、Discord、X 的多语言反馈瞬间涌入，角色争议几小时就能发酵；客服工单同步冲峰。这套流程每六周完整碾过来一遍。」 落到自己 · 30s 「这些环节全是高频、有 SOP、依赖专家经验的——正是我判断『值不值得 Agent 化』的标准。舆情客服和我做的智能排障是同构问题：事件流进来、按专家 SOP 分诊、处理不了升级给人。排障我们做到每周自动处理两万次、Oncall 降 40%。」 收口 · 10s 「打法是：先拆链路找高频有 SOP 的环节，优先做有真值、可评测的，再用评测和 Harness 保证生产可用——不是做个 demo 就叫落地。」
R2 · 项目深挖（Flux）+ 虚荣指标接刀 7.0 / 10

【题】挑一个项目讲透：背景痛点 / 切入点 / 方案 / 你个人的关键决策 / 数字怎么核。追问：周活口径？交付效率量过吗？为什么是你们团队做？你的周活和你批评的 token 消耗量有什么本质区别？

【保留】做对的部分
  • 两个决策故事是真货：①协作助理 vs 简单共享区——「没有无所谓、做不好会被喷」的期望管理；②自研 Agent vs 编排 SOTA——起步速度、迁移成本、能力不可能碾压。明天必讲。
  • 问题框架「个人提效 ≠ 组织提效，卡点在研发的上下游」——立项洞察有差异化。
【雷】踩过的坑
  • 四分钟全程「我们」，「我」消失了——「个人决策」和「数字」两个显式子问题被漏掉（第二次漏答）。
  • 数字没有锚：周活口径答成「每天」；「留存 60–70%」没说是哪种留存、什么时间窗。铁律：报数字必带口径 + 分母 + 时间窗。
  • 亲手缴械：「周活和 token 消耗没有本质区别，可能就是虚荣指标」——把简历上最大的数字让掉了。坦诚 = 承认边界，不是缴械价值。
  • 「据我了解只有我们一家」——字节内部 TRAE、Coze、豆包侧工具团队都在桌上，这个答案显得不了解自家公司。
  • 决策故事缺「验证结尾」：分歧 → 判断依据 → 拍板 → 代价 / 被验证，最后一节今晚补上。
【示范】虚荣指标接刀 · 40 秒
「有本质区别。Token 消耗是成本指标，可以被摊派和浪费；周活加留存是行为指标，用户是用脚投票回来的——它还不能证明交付效率提升，但它是那个北极星的领先指标和必要条件。我们的路径是有意设计的：先用统一调度 SOTA Agent 这个刚需把人请进来，目前 X% 的活跃用户已渗透到共享 Context 功能——木马策略在生效。北极星那层，正在和 X 业务线共建对照，目标 Q3 拿到需求流转时长的前后对比。周活是脚手架，不是终点，而且我对『什么时候必须拿出终点数据』有明确时间表。」
【示范】为什么是你们 · 生态位答法
「相邻的玩家有：TRAE 解决个人编码、Coze 解决 Agent 搭建，都是个人 / 单 Agent 视角；我们卡位的是团队协作层 + 内场研发基建的深度集成——这是平台团队没有的资产。」承认竞争、讲清生态位，比「没有竞争」可信一百倍。
R3 · Agent 工程化（bad case 闭环 / 评测 / 发布） 7.0 / 10

【题】bad case 从发现到修复上线且不弄坏别的 case，闭环怎么转？追问：可用率 90% 谁打分？Agent 不确定性下 92%→89% 是真回归还是噪声？模型升级怎么发布？

【保留】做对的部分（主场证据链）
  • bad case 双渠道（内部 dogfooding + 反馈群）、trace 分析工具、用户不回复时上线代码反向 diff、修复分诊（工程 vs 效果 / 通用知识 vs 仓库级 skill）。
  • 双评测集防过拟合：研发自维护 + 评测团队独立保留集，原则上不许对保留集调优。
  • 打分三层：单测通过（客观真值）+ solution 要点 LLM 打分 + 人工抽检。
  • 发布：内部评测无明显劣化 → 灰度 AB → 线上信号；主动承认点赞点踩稀疏，加分。
【雷】踩过的坑
  • 硬伤：「跑三轮取最好」= pass@3，衡量能力上限；用户体验的是 pass@1——报出的 90% 系统性高估线上质量，且完全回答不了「真回归还是噪声」。
  • LLM judge 没标定——「裁判自己的准确率」被问了没接。
  • 模型升级缺两块：case 级翻转分析（总分持平但过的 case 换了一批）+ 行为指标（采纳 / merge 率、重试率、中途接管率，密度远高于点赞点踩）。
【示范】噪声与回归的正确答法
「报告指标用多轮平均或通过率，best-of 只看能力上限。回归判定不看总分看 case 翻转：一个 case 三轮里两轮以上从过变不过，才计为疑似回归，再人工看 trace 确认。评测集小，所以不迷信总分的小数点，看的是哪些 case 翻了、为什么翻。」
若实际就是取最好，主动降级：「严格说我们报的是 pass@3，是当时评测成本约束下的有意识取舍；回归判断主要靠 case 级翻转而不是总分。」——瑕疵包装成已知取舍，比被追问出来体面十倍。

今晚去查：judge 的人机一致率有没有数——这一个数字能把「我们有 LLM judge」升级为「我们标定过 judge」。

R4 · 发行 Case（星铁本地化链路 AI 化改造） 6.5 / 10

【题】6 周一版、几十万字翻成十几种语言，外包 + 人工质检，成本高、术语不一致、偶发文化合规事故。怎么拆？先做哪块？怎么评测？半年后拿什么数字证明值得继续投入？

【保留】做对的部分
  • 按内容类型拆 + 看清依赖：游戏内文本的译文是公告 / 物料翻译的上游 Context。
  • 历史版本翻译当评测集——自带 ground truth，冷启动成本极低。今晚最好的点子之一。
  • 合规前置 Research + 人工校验清单再注入（「召回率无法保证所以必须 human in the loop」）。
  • 产报告、主动暴露「哪些内容我没把握 + 路径」——不确定性外显。
【雷】踩过的坑
  • 合规只做了生成前，没做生成后。注入 Context 是约束不是保证，需要纵深防御：生成前注入 + 生成后独立合规检查器门禁 + 人工终审签字。且合规大头常在视觉物料（立绘、广告图），纯文本管线覆盖不到；禁忌清单应是分地区、版本化、与法务共建的长期知识库，不是每版临时查一遍。
  • 「Agent 是自由的，不是流水线」——业务负责人听到的词是「不可控」。发行要过法务、要有人签字担责：「多 Agent 对抗 Review 到没问题就给用户」的流程里，合规事故算谁的？没有具名签核节点，这套东西在发行体系一天都跑不起来。
  • 把自己的 Flux 经验忘了：自称「极致 Agent 用户，人只是驱动角色」——但发行运营和翻译外包不是 AI 原生人群。Flux 的 adoption 智慧原样搬过来：先当质检副驾 → 高置信段自动过 → 逐步放权。
  • 第三次漏答显式子问题（「要不要重排优先级」没有明确重排）。
【示范】组织与责任的答法（JD 第 3 条要的东西）
「Agent 的灵活性是实现手段，交付给业务的必须是有 SLA、有审计日志、有责任节点的流程：外包从『翻译者』转型为『审校者』；质检同学转型为『术语库和合规库的维护者 + 终审签字人』；几十万字按置信度分流——高置信直接过、低置信人工复核、合规敏感段强制签核。人没有被替掉，是被移到了杠杆更高的位置。」
【示范】半年证明 · 三族指标（每个利益方一族）
效率：一个版本本地化的端到端周期、单字成本、人工质检工时；质量：术语一致性错误率、返工率；风险：合规事故数、翻译类玩家舆情量。周期对比是好主意，但单独一个数扛不住追问。

稿一 · 自我介绍（约 2 分半，接动机 30 秒版） 开场必考
主线一句话 · 10s 「我这三年的主线，是围绕『如何让 Agent 真正服务好一个专业群体』做了三代产品，每一代的形态都跟着模型能力走。」 第一代 · 30s 「24 年模型还不具备端到端解决问题的能力，所以我们选了一个高频且痛的单点场景——研发 Oncall 排障，做最小闭环。我主导设计了基于 SOP 技能库的 Multi-Agent 架构，把专家的排障经验沉淀成可复用的技能。这个产品做到了每周自动化处理超 2 万次故障，Oncall 下降超 40%，MTTR 下降超 20%。」 第二代 · 30s 「25 年模型的长任务执行能力大幅提升，代码达到生产级水准，我们从垂直单点切到通用 Agent——Aime，服务字节全体研发。我负责的重点是效率层和 Harness：任务拆解、上下文构建、打通云环境测试验证，让 Agent 从『生成代码』升级为『可交付』。它做到了周活 7.5 万、渗透 90% 研发群体。」 第三代 · 40s 「26 年，用 Agent 写代码在字节已经是默认方式，但我们发现一个新问题：个人提效没有转化成组织提效——卡点转移到了研发的上下游。所以我发起了 Flux，一个面向团队协作的多 Agent 平台，用统一 Context 串起产品、设计、研发、测试的整条链路，上线后周活迅速破万、周留存〔今晚填口径和数〕。总结起来：24 年我在解决单点问题，25 年在解决个人效率，26 年在解决组织协作——底层逻辑始终是围绕 Context 和 Harness，让 AI 在生产环境里产出真实业务效果。」 桥接动机 · 5s（然后接 R1 卡里的动机 30 秒版） 「这也是我看发行 AI 这个方向的原因——」
稿二 · Flux 项目深挖（约 3 分钟） 权重最高
背景与洞察 · 40s 「立项背景是一个反直觉的观察：26 年初，字节内部几乎人人在用 Agent 写代码，公司层面也在追 token 消耗量这类指标——但 token 消耗并没有反馈到真实业务价值上，需求交付效率、人均交付需求数都没有明显变化。我们跟多个业务团队聊下来，发现卡点已经不在研发这里了，在研发的上下游：上游产品、设计这些角色用不好 AI 工具，需求流动速度跟不上开发速度，出现了木桶效应；下游的测试验证 Harness 没建起来——Agent 代码写得飞快，但接口测试、GUI 测试、造数据这些环节全是断点。」 方案 · 40s 「所以方案分两端。上游：给产品设计角色提供 AI 工具和实践，同时搭了一个协作空间——本质是一个共同产物的存放区，让上游的产出直接成为下游 Agent 的 Context。下游是苦活：围绕现有研发基建把测试 Harness 建起来——代码变更分析定位待测接口、结合业务知识智能造数做 Mock、用 Computer Use 跑 GUI 测试。」 我的两个关键决策 · 60s 「讲两个我拍板的决策。第一个：团队里有人想做『协作助理』——主动催办、帮你解决问题，听起来性感。我否了，因为这类能力属于『没有无所谓、做不好必被喷』——预期管理上是负资产。我定的原则是只做足够简单、足够有把握的事，先建立『这个产品很专业』的信任。验证：〔今晚填：上线后共享区使用率 / 用户定性反馈〕。第二个：要不要自研一个完整 Agent。我选了不自研，做 SOTA Agent 的统一编排——理由三条：自研起步太慢；用户已有习惯的 Agent，迁移成本真实存在；能力上不可能碾压 Codex 和 Claude Code。验证：〔今晚填：接入后调度量 / 用户增长数据〕。」 结果与坦诚边界 · 40s 「结果：上线后周活迅速破万——口径是〔今晚填：完成过一次 Agent 任务的去重用户 / 周〕，周留存〔填口径〕在 60–70%。我很清楚这还是领先指标：留存证明用户持续感知到价值，但北极星是需求交付效率。我们的路径是有意设计的木马策略：先用统一调度 SOTA Agent 这个刚需把人请进来，目前〔填〕% 的活跃用户已经渗透到共享 Context 功能。北极星那层，正在和〔填〕业务线共建对照组，目标 Q3 拿到需求平均流转时长的前后对比。」 为什么是我们 · 15s（被问才说） 「内部相邻玩家有：TRAE 解决个人编码、Coze 解决 Agent 搭建，都是个人 / 单 Agent 视角；我们卡位的是团队协作层加内场研发基建的深度集成，这是平台团队没有的资产。」
稿三 · Bad Case 闭环与评测体系（约 2 分半） 主场·打出统治力
先报结构 · 5s 「这个闭环分五步：采集、归因、修复、回归、发布。」 采集与归因 · 40s 「采集双渠道：自己团队 dogfooding + 大规模用户反馈群。归因上我们有 Agent rollout 的 trace 分析工具，能看到整个 loop 里调了哪些工具、读了哪些文件、耗时分布。执行时间长的，先定位卡点，一般是工程或 Harness 问题；效果差的，先找用户确认真实的改动逻辑和缺失知识；用户不回复的，我们拿他最终上线的代码和 Agent 生成的代码做 diff，再让 Agent 反向分析差在哪——这招把归因的死角堵上了。」 修复分诊 · 25s 「修复按类型分诊：工程问题走工程优化；知识欠缺的，通用知识进平台知识层，业务独立知识用标准化方式放进仓库——skill 和 knowledge 文档，验证有效后推给用户。」 回归与防过拟合 · 50s 「回归靠双评测集：研发自己维护一份，目标可用率 90% 以上；评测团队独立维护一份保留集，原则上禁止针对保留集调优，防过拟合。打分三层：先跑单测这个客观真值，再把关键修改点提炼成 solution 给模型打分，人工抽检兜底——judge 和人工的一致率是〔今晚填〕%。Agent 是不确定性系统，所以报告指标用多轮通过率，不用 best-of——best-of 只用来看能力上限；判断真回归还是噪声，不看总分看 case 翻转：一个 case 三轮里两轮以上从过变不过才计为疑似回归，再人工看 trace 确认。」 发布与模型升级 · 30s 「发布走灰度：内部评测集无明显劣化 → 线上 AB。线上信号不依赖点赞点踩——那个数据太稀疏——主要看行为指标：生成代码的采纳率、任务重试率、用户中途接管率。模型升级时基线滚动：旧模型就是本次基线，但除了总分还必须看 case 翻转明细，因为总分持平不代表没回归——可能过的 case 换了一批，业务关键场景恰好翻车。」
稿四 · 本地化链路 AI 化改造（约 3 分钟） Case·检验迁移力
先澄清再动手 · 10s 「先确认两个信息：现在合规事故大概什么频次、主要出在文本还是视觉物料？外包和内部质检的分工边界在哪？（现场问，问对问题本身加分）」 拆解与排序 · 50s 「我按严重度 × 频率两个维度排优先级，不只看量。第一优先是合规——术语不一致是玩家骂两句，合规事故是下架和公关危机，严重度天花板。而且合规适合先做，因为它是『检查器』不是『生成器』：不动现有产线、失败模式安全（拦下来给人看）、上线风险最低。第二是游戏内文本翻译——量最大、人工校验成本最高，且它的译文和术语表是公告、营销物料翻译的上游 Context，先做它，下游全部受益。第三才是公告和物料，消费上游沉淀的术语库，边际成本很低。」 合规怎么做 · 35s 「合规做纵深防御，三道闸：生成前，建分地区的合规知识库——和法务、本地团队共建、版本化维护，不是每版临时 Research；生成后，独立的合规检查器做门禁，因为把规则注入 Context 只是约束、不是保证；最后人工终审签字——合规这种事必须有具名责任人。另外它要覆盖视觉物料，服饰禁忌大头在立绘和广告图，不只是文本。」 翻译与评测 · 40s 「翻译主攻一致性和准确性。第一步先把历代版本的官方译文提炼成术语库和风格库——角色名、技能名的多语言对照表，这是整条链路最值钱的 Context 资产。评测有个天然优势：历史版本的人工译文就是现成的评测集，自带 ground truth，冷启动成本极低。术语一致性甚至不需要 LLM 打分——对着术语表跑规则校验就行，便宜又准；语言风格才用 LLM judge 加人工抽检。」 工作流与组织 · 35s 「交付的不是一个翻译模型，是一条有 SLA、有审计日志、有责任节点的新流程：机翻打底 → AI 自检（术语、合规、风格）→ 按置信度分流——高置信直接过、低置信人工复核、合规敏感段强制签核。外包从『翻译者』转型为『审校者』，质检同学转型为『术语库和合规库的维护者 + 终审签字人』。人没有被替掉，是移到了杠杆更高的位置——这也是我在 Flux 上验证过的 adoption 路径：先当副驾建立信任，再逐步放权。」 半年证明 · 20s 「半年后拿三族指标：效率——一个版本本地化的端到端周期、单字成本、人工质检工时；质量——术语一致性错误率、返工率；风险——合规事故数、翻译类玩家舆情量。每个利益方一族，单一数字扛不住追问。」
